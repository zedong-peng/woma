# Security

Woma packages can install agent instructions, MCP process definitions, and Agent lifecycle hooks. Treat a package like executable code.

- Review `woma.yaml`, every `SKILL.md`, hook command, and referenced script before activation.
- Pin Git sources to an immutable commit or signed release for production use.
- Manifests declare environment variable names only. Never put credential values in a manifest.
- `capture` rejects literal MCP environment and header values instead of exporting possible secrets.
- `woma-package-builder` must copy only user-selected resources and environment variable names when wrapping existing Agent content. It must not copy credential values, authentication state, sessions, history, or unrelated Agent configuration into a Package.
- Skill directories containing symbolic links are rejected so package content cannot escape its root during installation.
- On first implicit `base` creation only, Woma may inspect filesystem metadata for the fixed documented Codex/Claude Skill and session migration paths so it can display migration guidance. It does not enumerate names, read contents, follow symlinks, hash or copy state, or store detection details. Explicit `woma migrate skills` validates a complete temporary snapshot before installation, leaves original directories unchanged, excludes hidden Agent-managed Skills, and fails closed on source or target ownership conflicts. Review existing Skills before migration because the resulting Package is exportable.
- Before every Skill or session migration, including dry runs, Woma checks the current user's process table for Codex and Claude CLIs. Detected Agent processes require an explicit interactive `yes`; non-interactive migration fails closed.
- `woma list`, `woma info`, and `woma doctor` discover Environment-local Skills by enumerating non-hidden direct children of the selected Environment's shared `home/skills` directory and parsing only `SKILL.md` frontmatter. Discovery does not hash, copy, relink, package, or export their contents. Invalid metadata is reported, name conflicts fail `doctor`, and `.system` is excluded.
- Explicit `woma migrate sessions` copies only documented session and history paths into the selected stable Agent home. It rejects source symbolic links and special files, verifies that the source did not change while the temporary snapshot was built or before publication, and fails before publication on different same-path target content. A legacy target link is accepted only when it points directly to the corresponding path in the selected source tree, then replaced with ordinary Environment-owned state. JSONL history is parsed as objects, deduplicated by canonical full-record identity, and atomically replaced after merging. The resulting ordinary files are private Environment state, are not exportable Package content, and no longer depend on the original home.
- Content-addressed Package entries are published without write permission. Their Environment Skill links are read-only views; use Woma repair paths rather than editing Store contents. To remove an entire development `WOMA_HOME` manually, restore owner write permission first with `chmod -R u+w "$WOMA_HOME"`.
- Project-scoped MCP servers still require the trust and approval flow of the target agent. Pi MCP servers and Hooks are rejected because the Pi adapter currently supports Skills only. Qoder MCP servers and Hooks are written into the managed per-Environment `settings.json`; Woma never captures, migrates, or seeds Qoder credentials or sessions.
- Activation refuses conflicting skills and MCP entries. Deactivation leaves user-modified artifacts in place.
- Activation never creates project instruction or context files. As a compatibility cleanup, it may remove only exact legacy Woma or Harness Project Memory discovery blocks from `AGENTS.md` and `CLAUDE.md`; modified blocks fail closed, surrounding content, symbolic links, and file modes are preserved, and Memory data is never read or changed.
- Stable per-Environment Agent homes, the shared Skill root, and views may contain credentials, provider configuration, sessions, databases, installed Skills, and other private state. Original Codex and Claude configuration seeds credentials and provider settings only when an Environment is initialized; subsequent edits and explicitly migrated sessions are Environment-specific. Every target Agent's `skills` path links to the Environment's shared `home/skills` directory. A Pi Environment otherwise starts with an empty stable home, and Pi owns every non-Skill path under `$PI_CODING_AGENT_DIR`. A Qoder Environment likewise starts without copied credentials, and Qoder owns every path under `$QODER_CONFIG_DIR` except the Woma-managed `settings.json` and shared `skills` link. Woma creates homes and views with user-only permissions; protect `$WOMA_HOME` like the original Agent configuration directories and never publish it.
- Outside the documented explicit session migration paths, Woma never copies or transfers unknown Agent state between Environments. The one-time legacy Skill-layout upgrade moves unique non-Woma entries intact from separate target roots into the same Environment's shared `home/skills` directory. For same-name entries only, it reads and hashes the complete trees to deduplicate verifiably equivalent copies; differing content, executable bits, link semantics, or unsupported filesystem objects fail before mutation. It also preflights Package ownership, rechecks equivalent copies immediately before moving, and rolls ordinary publication failures back. SQLite main, WAL, and SHM files remain opaque in one stable Environment home and are excluded from Package locks and bundles.
- Codex owns the representation and contents of the hidden `home/skills/.system` entry in each Environment. Woma neither validates nor rewrites it, and excludes it from generated views, Environment-local Skill inventory, Package Store entries, locks, migration snapshots, and bundles. Because target Skill paths share one Environment root, other target processes can reach the filesystem entry even though it is not advertised as an ordinary Skill.
- Environment recipes and locks contain package metadata, sources, and integrity values, but never environment-variable values or Agent prompts.
- `.woma-env` bundles contain the complete locked Package closure and must be treated like executable code. Import validates size limits, paths, identities, dependency edges, and integrity before publishing an Environment. Bundles exclude Agent homes, credentials, sessions, databases, environment-variable values, and all project files, but private Package source and file contents remain private and must not be uploaded unintentionally.
- Woma does not define, read, write, inject, package, or delete Agent Memory or project context. Keep credentials out of whichever context system the Agent or user chooses.
- Environment selection is stored only in the current shell's `WOMA_ENV` and is never written into a project or uploaded by Woma.

Report vulnerabilities privately to the repository owners. Do not include credentials or private Woma packages in an issue.
